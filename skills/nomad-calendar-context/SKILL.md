# nomad-calendar-context

## Purpose

Read a narrow, read-only Apple Calendar snapshot and turn it into schedule context for Nomad Life.

This Skill is a local app context agent. It does not decide the user's day by itself. It gives structured context to `nomad-coordinator`, `nomad-rest`, and `nomad-travel-guide`.

## Input Data

- Apple Calendar events for today and the near future
- Event title
- Start and end time
- Calendar name
- Location, when available
- All-day flag

## Read Locations

```txt
data/context/calendar-context.json
data/action_logs/YYYY-MM-DD.jsonl
```

The context file is generated by:

```bash
scripts/read_calendar_context.py
```

Or through the daily runner:

```bash
scripts/run_nomad_daily.py --include-local-apps
```

## Available Tools

- Local files
- Terminal script
- Swift EventKit bridge
- Hermes read-only review

## Procedure

1. Read `data/context/calendar-context.json`.
2. Check `data_quality.status`.
3. If status is `unavailable`, report the permission or bridge issue without pretending calendar data exists.
4. If events exist, summarize schedule density and obvious time pressure.
5. Look for travel, appointment, work block, social, and recovery signals.
6. Pass only interpreted context to Coordinator.
7. Do not create, edit, delete, or move calendar events.

## Output Shape

Calendar context should be consumed as:

```json
{
  "agent_name": "nomad-calendar-context",
  "status": "empty | partial | unavailable",
  "event_count": 0,
  "timed_event_count": 0,
  "schedule_density": "unknown | light | medium | heavy",
  "signals": [],
  "risks": [],
  "recommendations": []
}
```

## Do Not

- Do not write to Apple Calendar.
- Do not assume missing events mean free time if access is unavailable.
- Do not expose private event details unnecessarily in daily summaries.
- Do not suggest schedule changes as already approved.
- Do not treat calendar context as more important than the user's explicit capture.

## Example

If calendar context has five events tomorrow:

```txt
일정 밀도가 높습니다. 내일은 새 작업을 추가하기보다 이동/준비/회복 시간을 먼저 보호하는 것이 좋습니다.
```
